Micronaut JMS

Integration between Micronaut and Java Messaging Service (JMS)

Version: 5.2.0-SNAPSHOT

1 Introduction

This project includes integration between Micronaut and Java Messaging Service (JMS).

Supported implementations include Active MQ "Classic", Active MQ Artemis, and AWS SQS, and configuring other JMS providers is straightforward.

2 Release History

For this project, you can find a list of releases (with release notes) here:

https://github.com/micronaut-projects/micronaut-jms/releases

3 Breaking Changes

5.0.0

The way of configuring unsupported brokers has changed. See the Customizing Brokers section.

4.0.0

Removal of javax.jms namespace

Version 4 switches from the deprecated javax.jms namespace to the new Jakarta EE jakarta.jms namespace.

ActiveMQ Classic

The ActiveMQ Classic client has been updated to version 6 to support the new namespace.

ActiveMQ Artemis

The client dependency for ActiveMq Artemis has changed from org.apache.activemq:artemis-jms-client to org.apache.activemq:artemis-jakarta-client which uses the new namespace.

Deprecations

  • The annotation io.micronaut.jms.annotations.Queue removes the following attributes that were deprecated previously. This is to align the implementation with the JMS model and the messaging libraries' presumptions.

    • String concurrency() default "1-1"

    • String executor() default ""

  • The annotation io.micronaut.jms.annotations.Topic removes the following attributes that were deprecated previously. This is to align the implementation with the JMS model and the messaging libraries' presumptions.

    • String executor() default ""

  • The following classes in the io.micronaut.jms.listener package were deprecated previously are now removed.

    • ConcurrentMessageHandler

    • JMSListenerContainer

    • JMSListenerContainerFactory

Creating a JMS Consumer with @JMSListener

To listen to JMS messages you can use the @JMSListener annotation to define a message listener.

The following example will listen for messages published by the TextProducer in the previous section:

import io.micronaut.jms.annotations.JMSListener;
import io.micronaut.jms.annotations.Queue;
import io.micronaut.messaging.annotation.MessageBody;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

import static io.micronaut.jms.activemq.classic.configuration.ActiveMqClassicConfiguration.CONNECTION_FACTORY_BEAN_NAME;

@JMSListener(CONNECTION_FACTORY_BEAN_NAME) // (1)
public class TextConsumer {

    List<String> messages = Collections.synchronizedList(new ArrayList<>());

    @Queue(value = "queue_text") // (2)
    public void receive(@MessageBody String body) { // (3)
        messages.add(body);
    }
}

5.4 Configuring Unsupported Brokers

Using an unsupported JMS broker is simple; you simply need to instantiate a ConnectionFactory and JMSConnectionPool in a Bean factory. See the Replacing the ConnectionFactory section below for an example.

With this in place you can configure consumers and producers that use the connection factory by referencing the bean name ("myConnectionFactory" in the example) in @JMSProducer and @JMSListener annotations on your producer interfaces and consumer classes.

5.5 Customizing Brokers

Although only the broker URL is configurable in application.yml, there are potentially many configurable properties in the instantiated ConnectionFactory. Also, you may wish to use a different ConnectionFactory implementation class. Any customization you need can be done by intercepting the creation of the ConnectionFactory with a BeanCreatedEventListener.

Customizing the ConnectionFactory

Here we intercept the creation of the ActiveMQ "Classic" ConnectionFactory by overriding the default to enable asynchronous message sending:

import io.micronaut.context.event.BeanCreatedEvent;
import io.micronaut.context.event.BeanCreatedEventListener;
import jakarta.inject.Singleton;
import org.apache.activemq.ActiveMQConnectionFactory;

import jakarta.jms.ConnectionFactory;

@Singleton
public class CustomizeBrokerJMSConnectionPoolListener implements BeanCreatedEventListener<ConnectionFactory> {

    @Override
    public ConnectionFactory onCreated(BeanCreatedEvent<ConnectionFactory> event) {

        ConnectionFactory connectionFactory = event.getBean();
        if (connectionFactory instanceof ActiveMQConnectionFactory) {
            ActiveMQConnectionFactory amqcf = (ActiveMQConnectionFactory) connectionFactory;
            amqcf.setUseAsyncSend(true);
        }

        return connectionFactory;
    }
}

6 Parameter Binding

Methods in classes/interfaces annotated with @JMSProducer and @JMSListener use parameter binding annotations to access the JMS Message, message body, and message headers.

@MessageBody

The MessageBody annotation is required for the method argument that will be serialized/deserialized as the JMS Message body.

@MessageHeader

The MessageHeader annotation is required for any method arguments that will be serialized/deserialized as JMS headers or non-JMS headers (message properties).

In this example, the message body is a Map and the method supports sending the JMSCorrelationID along with several custom header values:

import org.jspecify.annotations.Nullable;
import io.micronaut.jms.annotations.JMSProducer;
import io.micronaut.jms.annotations.Queue;
import io.micronaut.messaging.annotation.MessageBody;
import io.micronaut.messaging.annotation.MessageHeader;
import java.io.Serializable;
import java.util.Map;

import static io.micronaut.jms.activemq.classic.configuration.ActiveMqClassicConfiguration.CONNECTION_FACTORY_BEAN_NAME;
import static io.micronaut.jms.model.JMSHeaders.JMS_CORRELATION_ID;

@JMSProducer(CONNECTION_FACTORY_BEAN_NAME)
public interface MapProducer {

    @Queue("queue_map")
    void send(@MessageBody Map<String, Serializable> body,
              @MessageHeader(JMS_CORRELATION_ID) @Nullable String correlationId,
              @MessageHeader("CustomStringHeader") @Nullable String stringHeader,
              @MessageHeader("CustomBooleanHeader") boolean booleanHeader,
              @MessageHeader("CustomByteHeader") byte byteHeader,
              @MessageHeader("CustomShortHeader") short shortHeader,
              @MessageHeader("CustomIntegerHeader") int intHeader,
              @MessageHeader("CustomLongHeader") long longHeader,
              @MessageHeader("CustomFloatHeader") float floatHeader,

Session

A listener method can declare a parameter of type jakarta.jms.Session, without a binding annotation, to receive the session that consumed the message, for example to reply on that session. A parameter typed as a provider subtype of Session, such as Oracle’s oracle.jakarta.jms.AQjmsSession from aqapi-jakarta, receives the session when it is of that type. When it is not, the application fails to start. Oracle’s oracle.jms.AQjmsSession, from aqapi, implements javax.jms.Session instead, and is not recognised as a session: like any other listener parameter without a binding annotation, it fails the application at startup.

With transacted = true, the listener commits the session when the method returns and rolls it back when the method throws, so messages sent on the session commit together with the receipt of the message. With Oracle Transactional Event Queues, SQL run on the session’s database connection commits with them too. The following listener confirms each order in the same transaction as its receipt:

Producer sessions

Producer methods reuse their sessions. For each connection factory, they open one connection and keep up to max-idle idle sessions for each session mode, plain or transacted. Each send borrows a session, so concurrent sends use different sessions, and a session on which a send failed is closed rather than reused. The connection and its sessions are closed with the application context.

At most max-active sessions of a connection factory are borrowed at once, of all session modes. When all of them are borrowed, for example during a burst of asynchronous sends, a send waits up to max-wait for another send to release its session. A session released while sends wait is kept for them, so a burst reuses at most max-active sessions of each session mode rather than closing and opening sessions. Once no send waits, the idle sessions above max-idle are closed: when they are released, or within 30 seconds otherwise. If none is released in time, the send fails with a MessagingClientException: a synchronous method throws it, a returned future completes exceptionally and a returned publisher signals the error. Nothing is sent in that case.

If a session cannot be created, or the JMS provider reports to the connection’s ExceptionListener that the connection failed, the connection is replaced. Its idle sessions are closed, and sessions that sends are still using are closed when they are released, rather than reused. The old connection is closed once the last of its sessions is, so sends in progress on it are not interrupted.

Before setting consumers above 1, note that:

  • The listener bean is still a single instance, and its method now runs on several threads at once, one per consumer. The listener must be thread-safe: the example guards its state with a synchronized set and an atomic counter (a lock in Python).

  • Messages are no longer processed in the order they were sent, since each consumer handles the next message it receives while the others are still busy.

  • If a consumer fails to start, the method keeps none of its consumers: the consumers already started are stopped and their connection is given back (returned to the pool, or closed if it is dedicated). A JMSException is logged and the application starts without the method’s consumers; any other failure stops startup.

On a topic, every consumer of a plain subscription receives every message, so consumers above 1 requires a shared subscription (see Durable and Shared Topic Subscriptions), whose consumers share the messages. An unshared durable subscription allows only one consumer. A shared subscription with a client ID can have several consumers: they share the one connection that holds the client ID.

Messages are then traced:

  • Sending a message creates a PRODUCER span named send <destination>, a child of the current span. It starts before the connection is taken, so a send that fails to connect ends it with an error too. The trace context is propagated to the receiver in message properties by the configured propagators.

  • Processing a message creates a CONSUMER span named process <destination> that continues the trace of the sender. It is the current span while the listener method and the success and error handlers run, so spans created by the listener method are its children. It is also current in Micronaut’s propagated context, so it follows the listener method to the threads that the context propagates to. A failure sets the span’s status to ERROR and records the exception.

Custom observers

The metrics and the tracing are beans of type JMSMessageObserver. Other beans of that type are also called before a listener processes a message and before a producer sends one, and the observation each returns is completed afterwards with the error, if any. A producer’s observation starts before the connection is taken, and its beforeSend method is called with the message once the message is created, so properties set on it are sent. A listener’s observation can give, from its propagatedContext method, the propagated context that the listener method and the handlers run in. Observers are called in order, and their observations are completed in the reverse order. A JmsProducer created by the application only calls the observers added with addObservers.

Client IDs

JMS identifies an unshared durable subscription by the connection’s client ID together with the subscription name, and a client ID can be set only once per connection. Micronaut JMS therefore gives each unshared durable listener its own connection, outside the connection pool, with the client ID set from clientId. When clientId is not set, the subscription name is the client ID.

Set clientId when a broker administrator has assigned one, or to give a shared subscription a client ID. A listener with a clientId always gets its own connection. Shared subscriptions without one use a pooled connection.

A client ID can be in use by only one connection at a time. Do not run two instances of an application with the same unshared durable listener against one broker; use a shared durable subscription to spread the messages between instances.

durable, shared and clientId require subscription, and subscription requires durable or shared. Micronaut JMS fails at startup if either is missing. Shared subscriptions need a JMS 2.0 broker, such as ActiveMQ Artemis. ActiveMQ "Classic" supports only unshared durable subscriptions: a shared listener on it fails to register, which is logged like any other registration failure.

16 Listener Session Recovery

A listener recovers when the JMS provider reports that the session of one of its consumers died, so that the consumer doesn’t stop receiving messages until the application restarts.

What Triggers Recovery

When the JMS provider reports an error through the ExceptionListener of a listener’s connection, each consumer of that connection checks its session by looking up its destination. Only a consumer whose session fails that check recovers. Errors that leave the session usable don’t recreate anything, such as the rejected asynchronous send that ActiveMQ "Classic" reports while its connection still works.

For example, when the database session of an Oracle AQ listener is disconnected, AQ reports JMS-120: Dequeue failed, and later JMS-112: Connection is invalid on each of its pings. A new session on the same connection still works, so the listener recovers.

What Is Recreated

The consumer closes its session and MessageConsumer and creates them again on the same connection, with the same message selector and subscription. A durable or shared subscription resumes on the same subscription, and the provider redelivers the messages that weren’t acknowledged.

If the session or consumer can’t be created, the consumer tries again after a delay that doubles after each attempt, up to a maximum. It keeps trying until it succeeds or the application shuts down, since the provider may report nothing more once the failed session is closed. io.micronaut.jms.listener.JMSListenerRegistry logs the first attempts as warnings and later ones as errors.

  • A connection that fails as a whole isn’t replaced. For example, when an ActiveMQ broker restarts without a failover transport, only the session is recreated, on the same connection.

  • A consumer that is still recovering doesn’t change the jms health indicator.
